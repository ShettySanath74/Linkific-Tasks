# Dimensional Modeling Guide — Day 11

## 1. Data Warehouse Concepts

### OLTP vs. OLAP

**OLTP (Online Transaction Processing)**
- Handles operational transactions.
- Supports inserts, updates, and deletes.
- Example: creating an order or updating a customer's address.

**OLAP (Online Analytical Processing)**
- Supports analytical queries and reporting.
- Commonly uses aggregations across large datasets.
- Example: calculating monthly revenue by product category.

### Database vs. Data Warehouse vs. Data Mart

- **Database:** Stores and manages application data.
- **Data warehouse:** Integrates data for analytical reporting and historical analysis.
- **Data mart:** A focused subset of analytical data for a business function, such as sales.

### Common Architecture Layers

1. **Source:** Operational databases and external systems.
2. **Staging:** Extracted data prepared for validation and transformation.
3. **Warehouse:** Integrated fact and dimension tables.
4. **Presentation:** Reports, dashboards, and analytical queries.

## 2. Dimensional Modeling

Dimensional modeling organizes data into fact tables and dimension tables.

### Fact Tables

A fact table records business events and measurable values.

In this project, `fact_sales` contains:
- Order and order-item identifiers
- Customer, product, date, and store keys
- Quantity and unit price
- Sales amount

### Dimension Tables

Dimension tables provide descriptive context.

- `dim_customer`: customer details and historical versions
- `dim_product`: product and category information
- `dim_date`: calendar attributes
- `dim_store`: store and sales-channel details

## 3. Star, Snowflake, and Galaxy Schemas

### Star Schema

A central fact table connects directly to dimension tables. It is easy to understand and supports common analytical queries.

### Snowflake Schema

Dimension attributes are normalized into additional related tables. This can reduce duplicated descriptive data but introduces more joins.

### Galaxy Schema

Multiple fact tables share common dimensions. For example, sales and inventory fact tables might share product and date dimensions.

**Project choice:** This project uses a star schema.

## 4. Fact Table Grain

The grain describes exactly what one fact row represents.

For `fact_sales`, the grain is:

**One row per product line within a sales transaction.**

Defining the grain before selecting measures and keys prevents incorrect aggregation and duplication.

## 5. Measures and Attributes

### Measures
- Quantity sold
- Unit price
- Sales amount

### Attributes
- Customer city
- Product category
- Calendar month
- Sales channel

Measures support calculations; attributes support filtering, grouping, and reporting.

## 6. Natural Keys and Surrogate Keys

A **natural key** originates from a source system, such as `customer_id`.

A **surrogate key** is generated by the warehouse, such as `customer_key`.

SCD Type 2 uses a new surrogate key for each historical version of a customer.

## 7. Slowly Changing Dimensions

### Type 1 — Overwrite

Updates a value directly. Previous values are not retained.

### Type 2 — Add a New Version

Retains the old row and inserts a new row when a tracked attribute changes.

Typical fields include:
- `effective_start_date`
- `effective_end_date`
- `is_current`

### Type 3 — Previous Value

Adds a column to retain a previous attribute value. This captures limited history rather than a full sequence of versions.

## 8. Data Quality and Validation

Before loading warehouse data:
- Validate required fields.
- Check source identifiers for duplicates.
- Validate foreign-key references.
- Ensure fact measures are valid.
- Check that each customer has at most one current dimension version.
- Confirm analytical totals against the underlying fact records.

## 9. Conclusion

Dimensional modeling provides a structured foundation for analytical reporting. The e-commerce warehouse demonstrates how fact tables, dimensions, surrogate keys, and SCD Type 2 can support sales analysis while preserving customer history.
